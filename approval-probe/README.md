# Approval capability probe — synthetic only

This is not a live approval bridge. It asks the MCP client to present one non-sensitive, exact, synthetic action using form elicitation, and never creates even a mock provider draft. An MCP JSON-RPC response can only be treated as a human action after verifying the installed host presents a real blocking prompt; a synthetic transport response is not human approval. The tested endpoint will not accept approval through tool arguments or accept a stale/incorrect request ID.

On the exact Mac and Claude Desktop version, the test is in normal Chat. If the host doesn't declare form elicitation or doesn't display the full caption, exact asset identifiers and target, stop. Test decline, system cancel, wrong/current request and repeat needing a new response, including Auto and an always-allowed tool setting. Allow-once is not a durable security guarantee if the host allows overrides, truncates details or fails to prove binding. Keep provider writes disabled until native behavior is independently verified.

References: Anthropic local Desktop extensions and per-tool approvals; MCP 2025-11-25 Elicitation; Apple Secure Enclave key protection and userPresence. If macOS confirmation is needed, investigate a signed P-256 Secure Enclave signer with a new local authentication context per operation, a non-reusable nonce and exact immutable action details (not just a generic Touch ID prompt). Existing Ed25519 fixture is not a Secure Enclave implementation. Verify cancellation, repeated prompts (no cached approval), and rejection of modified action, stale nonce and missing hardware on the target Mac before wiring. No separate recurring UI or terminal required as a product design assumption; this is not yet proven on Mac.
